# 盲點檢查

學員說「我做好了」的時候，**他通常是對的一半**。
最貴的那一半是：畫面上看起來都對，但真正上線的時候什麼都不會發生 —— 而且沒有錯誤訊息。

你的任務是拿**證據**回答「好了沒」，不是問他感覺如何。

## 第一件事：跑檢查，不要用讀的

```bash
python3 scripts/check_setup.py
```

⛔ **不要靠讀 code 判斷他做好了沒。** 檔案裡寫著什麼，跟 GitHub 上實際的狀態是兩回事 ——
secret 有沒有設、Actions 有沒有啟用、workflow 有沒有真的跑成功，都不在檔案裡。

沒裝 `gh` 或沒登入時，有三項會回 ❔。**❔ 不等於通過** ——
要老實告訴他那三項你驗不了，並給他自己去頁面上看的路徑。

## 七項在查什麼、為什麼

| 項目 | 沒做到的症狀（這才是他該記住的）|
|---|---|
| config.yaml 換過了 | 他辛苦跑完，追的還是課程預設的三個網站 —— 不是他的東西 |
| `contents: write` 還在 | Actions **綠燈**、程式**有跑**，但報告永遠不會出現 |
| 測試綠 | 改壞了不知道，下次它在半夜自己失敗 |
| 報告真的存在 | 「應該有跑吧」跟「檔案在這裡」是兩件事 |
| Actions 已啟用 | fork 來的 repo 預設不跑。設定全對，就是不會動，也不報錯 |
| secret 設好了 | 報告會產出，但摘要那段是「⚠️ 沒有 GROQ_API_KEY」|
| 真的跑成功過 | 沒手動跑過的人，會在下週一早上才發現沒設好 |

## 怎麼回報給他

**先講結論，再講細節。** 開頭一句話說清楚「能不能放著不管了」，不要用一堆綠勾淹沒他。

- 全過 → 「可以放著不管了。每週一早上九點它會自己跑」
- 有 ❌ → 「還不行，卡在 N 個地方，我們一個一個修」，然後**從最擋路的那個開始**
  （順序：Actions 啟用 → secret → 寫入權限 → 其他）
- 有 ❔ → 「有 N 項我在這裡驗不了，你要自己去頁面上看」，並給他確切位置

修的時候維持**一次一個**。修完**重跑一次檢查**才算數，不要用「這樣應該就好了」收尾。

## 機器驗不到、但你該用眼睛看的三件事

檢查腳本只查得到結構，查不到品質。全綠之後再多看這三樣：

1. **打開最新那份報告，真的讀一次。**
   摘要是中文嗎？連結點得開嗎？他設定的每個來源都有出現嗎？
   有來源整個消失 = 那個 RSS 網址可能是錯的，但程式被設計成不會因此整份失敗。

2. **金鑰是怎麼給的。**
   如果他把 key 貼進了 `config.yaml`、程式碼、或任何會 commit 的檔案 —— 這是唯一
   需要立刻處理的問題：去 Groq 後台把那把 key 刪掉重發，再用 secret 的方式設一次。
   （課堂上為了現場方便把 key 貼給 AI，那是作弊版，講師自己有講。）

3. **這個自動化對他有沒有用。**
   問一句：「下週一收到這份報告，你會打開來看嗎？」
   他猶豫 = 追的來源不對，回去改 `config.yaml`，這比任何技術問題都值得修。

## 不要做的事

- ⛔ 不要因為他說「好了」就跳過檢查
- ⛔ 不要把 ❔ 講成「應該沒問題」
- ⛔ 不要一次丟七項給他修
- ⛔ 不要幫他把 secret 值印出來確認 —— 名字對就夠了，值本來就不該看得到
